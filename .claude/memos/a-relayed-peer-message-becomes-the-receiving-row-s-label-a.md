# A relayed peer message becomes the receiving row's LABEL, and its whole envelope is stored as a prompt

A relayed peer message becomes the receiving row's LABEL, and its whole envelope is stored as a prompt. The label then reads `[cross-machine message, relayed by the dashboard] Sender: agent "..."` — transport boilerplate where the task should be — and `prompt_history.json` holds the envelope verbatim, one of them 34KB. Measured on this machine 2026-09-13: 39 stored relay envelopes across four rows (tauri-dashboard, transcripts, what-is-next, and one on the Mac side). FOUND BY the AIR session, which reverted a hero re-shoot because a row it had created by messaging a peer showed this in frame. THERE ARE TWO ENVELOPE FORMS AND ONLY ONE IS HARMLESS — corrected 2026-09-13 after AIR pushed back, and the back-and-forth is worth keeping because both of us were half right. (a) The CROSS-MACHINE RELAY (`[cross-machine message, relayed by the dashboard]`, 43 here) carries NO socket path: its reply address is the loopback `POST http://127.0.0.1:9077/api/message`, and `messagingSocketPath` is resolved inside the receiving dashboard (`session_registry::inbox_for`) and never reaches the agent's text. (b) Claude Code's OWN LOCAL `SendMessage` between sessions on one machine is a different transport with a different preamble — `<cross-session-message from="uds:..." from-name="...">` — and it DOES put the sender's inbox address in the `from` attribute. Confirmed on this machine, `tauri-dashboard` dialog entry 990: `from="uds:\.\pipe\LOCAL\cc-msg-de0e9ecbe8fad7d35bb0cf6c4cc1d41e"`, the Windows named-pipe form; the macOS form is `uds:/tmp/cc-socks/<pid>.sock` and arrives here through dialog sync. Calibrate the alarm: the pipe name is an ADDRESS, not a credential — writing to that inbox needs the per-session `<pid>.<64hex>.key` file, which is not in the envelope — so this is internal plumbing in plain view rather than an exploitable secret. My first pass reported "no socket path" because I searched only inside relay envelopes, which was true and too narrow; AIR's first pass attributed the leak to the relay, which was the wrong transport. So the leak is mild and the LABEL is the real defect. WHY IT MATTERS BEYOND LOOKS: the label is what the widget shows, what `terminal_title::build_title` would carry, what the notification text builders read, and what the dialog sync pushes to every peer — so one relayed message puts several KB of routing boilerplate on all of those surfaces, and any screenshot containing such a row prints it. `docs/screenshots/screenshots.json` says nothing about this today, and the hero's staging steps are exactly where it would bite again. SHAPE OF A FIX, unsettled: the envelope is assembled by `peer_message::build_content` and arrives as an ordinary `UserPromptSubmit`, so the dashboard cannot currently tell it from a human prompt — the honest fix is probably for the adapter to recognise the `----- BEGIN RELAYED MESSAGE {nonce} -----` fence it already mints and label the row with the sender plus the fenced body, keeping the full envelope in the dialog where the history window can show it. Do NOT simply truncate: the first 80 characters are the least informative part of the whole string.
