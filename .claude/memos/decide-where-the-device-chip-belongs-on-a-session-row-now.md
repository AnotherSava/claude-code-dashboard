# Decide where the device chip belongs on a session row, now that every badge has moved inside the .name box.

PROMPTED BY a real confusion on 2026-09-07, asked twice and only answered on 2026-09-09: the dashboard showed two what-is-next rows and the reason was correct behaviour, not a bug. CHROME was running its own what-is-next while remote_history/AIR.json held AIR/what-is-next, so the widget rendered one local row and one synced row for two genuinely different sessions on two machines. Ruled out with evidence rather than reasoning: name_shared_by was never stamped above 1 across 8MB of widget.jsonl, so no row was merging sessions. THE PROBLEM is that both rows print the same name and the only thing distinguishing them is the device chip, which sits between the name and the state pill - so at a glance the duplicate reads as a dashboard fault rather than as two machines. THE TENSION is with the rule this session established and wrote into CLAUDE.md and SessionItem.svelte: every badge rides inside .name and the state pill is only ever the status, because a mark after the pill reads as a qualifier on the state, which is the one thing about these rows not in doubt. Which machine a session runs on is squarely a fact about the session, so by that rule the chip belongs with the name; it is outside it only because nobody looked. OPTIONS: (1) move .device inside .name after the id and before the badges, so a synced row reads as one label - what-is-next AIR - which is the change the confusion argues for, and .device already has flex-shrink so no CSS work is needed; (2) leave it and accept the rule has one unstated exception, which the code comments now name explicitly so it cannot be misread; (3) something else for the duplicate-name case specifically, since the chip is only load-bearing when two rows share a name and is redundant noise the rest of the time. Oleg said the current placement is ok and wanted this parked for a fuller discussion rather than changed now.
