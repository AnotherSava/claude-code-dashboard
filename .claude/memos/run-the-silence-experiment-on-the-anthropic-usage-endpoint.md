# Run the silence experiment on the Anthropic usage endpoint: stop polling entirely for 60…

Run the silence experiment on the Anthropic usage endpoint: stop polling entirely for 60 minutes, then make exactly ONE request with every response header captured. WHY: the open question from 2026-09-10 is why it takes HOURS to get out of the limiter when the one Retry-After ever observed was 832 seconds (~14 min). Two explanations fit everything seen so far and they need different fixes — either the window is genuinely long and Retry-After only ever reports the tail of it, or each request made while blocked extends it, in which case the 10-minute poll was renewing its own punishment indefinitely and the block-skip now shipped in usage_limits::poll_once already fixes it. A single request after a long verified silence separates them: if it succeeds, the window was being extended; if it is refused with a fresh multi-hour Retry-After, it was long all along. WHAT IS ALREADY IN PLACE: poll_once skips while `usage_cache.json` carries a live `blocked_until` and replays the stored sample so the bars keep a real figure (both observed live 2026-09-11), and the client now reads response headers before consuming the body, which is what made the 832 visible at all. HOW TO GET THE SILENCE: the app polls on a timer, so quit it rather than trying to hold it off, and do not run `deploy` during the hour — every deploy is a restart and a restart polls at the top of its loop. Record the full header set either way; the endpoint is undocumented and this is the only way its policy becomes knowable. EVIDENCE ADDED 2026-09-11 05:01, from a real 429 rather than a planted one: the block it set ran ~16 minutes (`in_ms` counted down 986182 -> 906502 across three skipped polls), which is the same order as the 832s seen on 2026-09-10 and nothing like the hours the question is about — so either the hours are many consecutive ~15-minute windows, each renewed by the next request, or the long refusals have a different trigger entirely. The first reading is the one the experiment tests. WHAT TRIPPED IT is also worth recording, because it is the remaining half of memo 1 and is NOT fixed: the app polls once at the top of its loop on every start, and a screenshot session that deploys and restarts the app six times in ten minutes therefore makes six requests no rate limiter will forgive. `request_refresh` now declines the *second* request per launch and `poll_once` skips while blocked, but neither touches the one-per-start. BUILT 2026-09-11, so the experiment starts from a cleaner baseline than the one that produced tonight's 429: a start now replays a sample younger than the poll interval and skips the opening poll, so a deploy costs zero requests, and a live deadline decides the sleep so a blocked poller no longer wakes every minute. The hours question is therefore still open on its own terms rather than confounded by our own request rate.
