# Two Claude Code instances sharing one cwd collide into a single dashboard row: the…

Two Claude Code instances sharing one cwd collide into a single dashboard row: the desktop app and a terminal session both in /Projects/landlord derive the same cwd-based chat_id. Last hook to fire wins the console_pids registration, so the terminal tab loses its status glyph and the row mixes two conversations. Needs a chat_id that distinguishes instances (agent_pid? session_id registry?) without fragmenting one conversation across a mid-session cd. [DONE, with the premise corrected. The row was NOT mixing two conversations: the desktop session's argv is `--session-id … --fork-session --resume <the terminal session's transcript>`, so it inherited that transcript wholesale (296 shared message ids, the terminal transcript silent after the fork) and one row showing one continuous thread was right. The console_pids half was fixed separately in a671196 (the hook's ancestor walk is bounded at its own claude process, so a tty-less desktop session writes no title at all rather than titling the tab that launched it). What was left was the destructive half — `AdapterOutput::Clear` called `remove_session(.., None, ..)`, i.e. unconditionally, so an exit or `/clear` in the abandoned tab would flush the merged dialog, stop the watcher and drop a row the live sibling was still using. Now gated by the pure `http_server::clear_permitted`: the row's owner is the `agent_pid` of whichever instance wrote it last (`liveness::AgentPids`, already overwrite-per-event), and a mismatched end signal is refused and logged `decision = "clear_ignored"`; unknown ownership on either side still defers to the end signal. Deliberately NOT done: distinguishing the chat_id per instance (a `landlord (2)` suffix or session_id-keyed rows). It would split a conversation the user forked on purpose, and the observed damage it would buy back is 8 title writes over 3 minutes in 84 days of widget.jsonl. `AgentPids`' own chat_id-keyed overwrite is likewise left alone — the reaper's unchanged-pid-and-quiet-`updated` guard already covers it, and a reaped row is recreated by the sibling's next event.]
