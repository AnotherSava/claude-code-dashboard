# The stale-tab detector misses the commoner rename.

Measured live 2026-09-03: the achievement-overlay tab was renamed to "ttt" in Windows Terminal; the dashboard then made 99 successful SetConsoleTitleW writes to that session's console (all logged ok=true, title advancing through the context percentage), Windows Terminal ignored every one of them, and zero title_pinned decisions fired. Cause, and it is by design rather than a bug: observe_caption requires the caption to parse_title (a status glyph plus a name), so an arbitrary custom name is skipped before pin_verdict is ever reached. That skip is the same rule that stops a stray shell or another app's window being pinned onto whatever row looks closest, so it cannot simply be loosened. Net effect: the detector only catches the narrow case where the custom name still looks like a title we wrote, which is what you get by accepting the name Windows Terminal pre-fills and pressing Enter. That is the dangerous case (the tab keeps showing a status that has stopped being true) and it is worth having, but it is probably the rarer user action. Docs were corrected to describe both cases rather than promising a badge for either. PROBED 2026-09-03, and the first verdict of unfixable was wrong. A throwaway probe logging every WinEvent the pid-scoped hook receives (not just the OBJID_WINDOW ones on_event keeps) settled two things over 95s of real tab switching plus a live rename. (a) Windows Terminal raises NO tab-level MSAA name change: 20 events, of which exactly one was not OBJID_WINDOW, and that one was OBJID_CURSOR (id_object -9, hwnd 0, empty text). So reading per-tab titles off the existing hook is dead, and it needs no COM or UIA attempt to confirm that. (b) But the unrecognized caption IS delivered to us and IS attributable, which is what the original verdict got wrong. Captured: the caption read the working-glyph title we wrote for achievement-overlay at 23:17:36, then read ttt at 23:17:38, same HWND, with no EVENT_SYSTEM_FOREGROUND between them; thereafter achievement-overlay never appeared as a caption again while ttt appeared four times, and the console kept accepting writes with the row moving from Working to Blocked. Two usable signals, both on the code path already running and needing no new dependency: ADJACENCY, a caption going from a title we wrote to one we did not on the same window with no foreground change is that tab being renamed (ambiguous on a first sighting against switching to an already-renamed tab, which is exactly what the existing two-sample rule absorbs); and ELIMINATION, a row whose written title stops appearing as a caption at the moment an unrecognized caption starts appearing (needs history, and is confounded by a tab simply never visited, so it corroborates rather than accuses). Real limits either way: both need the tab visited at least once, as today's detector does, and a session in a background window or a non-WT terminal never appears as a caption at all, so absence can never accuse on its own. The docs shipped in v1.12.0 say this case is not flagged, so they need revising too if this is built.
