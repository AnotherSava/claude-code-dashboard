# `terminal-tabs-windows.png` has a border on two of its four sides and hard cuts on the…

`terminal-tabs-windows.png` has a border on two of its four sides and hard cuts on the other two, so it is the one figure that fails the edge check. It is a CROP of Windows Terminal's tab strip rather than a window capture: it keeps the window's own translucent border along its top and left — measured (84, 84, 84) at alpha 142 — and its right and bottom are wherever `terminal-tabs-windows.ps1` measured the crop bounds, which is bare content at (46, 46, 46). On a dark page those two sides have nothing to stop the picture. The rule is `~/.claude/skills/documentation/SKILL.md`, whose wording covers this case exactly: "a region crop never does [bring its own edge]". NOT FIXED FROM HERE on purpose: it is the other machine's capture, its crop bounds are that script's own measurement, and a first pass that retouched two Windows frames from this side had to be reverted — see the correction below. The macOS side now has the tool: `dash.add_hairline` in `docs/screenshots/capture/lib/dashboard.py` strokes 2px of #BDBDBD (what macOS strokes a window frame with) at 4x supersampling, with `dash.has_own_edge` refusing to double up on a frame that already has one. Port both to the Windows lib and call it from the terminal-tabs script. THE TWO MEASUREMENT MISTAKES ARE WORTH MORE THAN THE FIX, because both produced confident wrong answers: (a) sampling only pixels above alpha 200 cannot see a translucent border at all, and reported plainly-bordered Windows frames as edgeless; (b) sampling only the top edge reported `work-intensity-macos` as bordered when three of its four sides were bare — it is a decorated window, but it carries `"theme": "Dark"` and a dark-themed NSWindow gets no light stroke, so its top row was just the title bar's own highlight (73, 73, 75). `has_own_edge` now walks in from all four sides and compares the outermost pixel with ANY alpha against one five pixels further in, requiring three of four to agree before it declares a frame already bordered.

DONE 2026-09-12. The crop now carries a 2px #BDBDBD edge on all four sides, applied from the macOS side so the committed file is correct today, and `terminal-tabs-windows.ps1` calls the same script after its save so a re-shoot keeps it. Three corrections to the text above, all made while doing it. The tool is no longer `dash.add_hairline` in this repo's lib: it is `hairline.py` in the documentation skill, which both platforms shell out to — machinery belongs to the skill, only the staging belongs to the project, and that rule is now written into the skill. It supersamples at 3x, not 4x. And it gained the fix the macOS frames needed after this memo was written: the band's coverage is normalised against the shape's own coverage, so an antialiased corner pixel keeps the full border colour instead of a blend with the content behind it — without that a curve reads thin, which is what macOS's own frames do differently (grey 189 at alpha 243, softness in the alpha). The stroke goes on AFTER the crop, never before, or the edge lands where the crop cuts it away. NOT VERIFIED ON WINDOWS: the .ps1 edit could not be run from here (no pwsh), though its BOM is intact and the addition is pure ASCII, which is what the lib's header warns about.

CORRECTION 2026-09-13. "A 2px #BDBDBD edge on all four sides" was true and still wrong, and the sentence is worth keeping as written because it shows how: it reports a *width* and a *colour written*, and the defect was in neither. The two sides that keep the window's own border keep its **alpha ~130** as well, so writing 189 into a translucent band leaves the page behind tinting it — all four sides agreed at 189 on a white page and read 111/189/111/189 on a dark one, plus antialiasing debris (141/255, 94/255) through the rounded corner. The fix is `--opaque`, a new flag on the skill's `hairline.py` passed only by this project's `terminal-tabs-windows.ps1`: it takes the ring's alpha to 255 where the ring is solid, leaves the outer fringe alone so the corner does not square, and thresholds the silhouette *before* the 3x upsample (interpolating first drags samples across a threshold that sits inside the alpha plateau, which is what made the speckle). Two attempts rejected first and recorded in the script so they are not re-tried: stroking only the cut sides, and stroking all four while preserving alpha. THE LESSON IS ABOUT THE CHECK, not the border: every assertion in that script measured the frame on one background, and a border can only be wrong relative to what is behind it. A claim about a picture on a dark page has to be tested on a dark page — which is exactly what the contact sheet's theme toggle is for, and it was not used.
