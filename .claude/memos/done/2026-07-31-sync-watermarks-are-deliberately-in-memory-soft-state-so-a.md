# Sync watermarks are deliberately in-memory (soft state) so a wiped remote_usage/ or…

Sync watermarks are deliberately in-memory (soft state) so a wiped remote_usage/ or remote_history/ self-heals on the peer's next restart — the receiver treats delta_from == 0 / ts > held_max as "complete state" replays. But the repair is restart-triggered only: a peer running for weeks never re-advertises, so a wipe here stays unfilled until it restarts. Usage has no catch-up endpoint (dialogs have GET /api/sync/dialog?id=&since=). Fix = periodic full re-advertise (reset watermarks every N hours) or a receiver-driven "I hold up to T" handshake. Do NOT persist the watermark — it's the sender's guess about the receiver's state, and persisting it makes divergence permanent. [DONE in ffa20c6 (`fix(sync): pull content instead of pushing deltas`), which took the receiver-driven option and went past it: the per-peer/per-session watermark is *gone*, not merely unpersisted, so the "don't persist it" warning holds by construction. Push now advertises only a `dialog_tip`/`usage_tip` and the receiver derives `since` from the entries it actually holds at the moment of asking, so it cannot drift and a dropped fetch self-corrects on the next push. Usage got the missing catch-up endpoint, `GET /api/sync/usage?since=` (`sync::usage_since` + `RemoteUsageStore::newest_ts`) — the restart-only repair gap is closed for both stores. Verified 2026-07-31 against the real CHROME peer over Tailscale: 7554 usage records at since=0, 0 at since=<tip>, 682 dialog entries, and zero `non-contiguous dialog delta discarded` since the new build (201 historically, last 2026-07-24).]
