# Confirm the subagent permission-prompt gate on its first real prompt, and read matched_on off it

The subagent-gate fix (subagent_gate.rs, AgentSession::subagent_gate) shipped on 2026-09-25 verified only against synthetic events posted to /api/event: a Waiting row went BLOCK on a subagent PermissionRequest and back to Waiting about 1s after a tool_result was appended to a fake agent-<id>.jsonl; SubagentStop and the session-scoped empty-background Stop released too. No real subagent permission prompt had reached the new build by the end of that session, so three things are still unobserved on live traffic: (1) that a real subagent PermissionRequest carries agent_id (the 2.1.281 binary's hook-input builder says it does, via toolUseContext.agentId); (2) that the tick finds the gated call and settles via tool_result; (3) whether the hook's tool_input ever equals the transcript's input. How to check: after the next workflow or Task agent hits a permission dialog (the dangerous-rm safety check is the common trigger), grep widget.jsonl for decision=subagent_prompt_open and the following subagent_prompt_settled on the same chat_id. Expect via=tool_result, and read matched_on: 'input' means the exact-input match works, while 'name' on every real prompt means the hook's tool_input never equals the transcript's and the doc sentences that say input is preferred should say so. A subagent_prompt_unmatched line instead means the file lookup or the matching failed; run python .claude/skills/investigate/investigate.py <row> for the chain. Once seen, update .claude/memory/hooks_research_findings.md (the agent_id and tool_input notes) and the residuals list in CLAUDE.md's subagent_gate.rs entry.
