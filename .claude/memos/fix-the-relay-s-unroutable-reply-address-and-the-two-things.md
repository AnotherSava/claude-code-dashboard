# Fix the relay's unroutable reply address, and the two things that made it cost three sessions a wrong diagnosis.

Reported by the what-is-next session on CHROME via the peer relay 2026-09-05, independently reproduced by the trips and printlab sessions on AIR; every claim below re-verified against this tree before recording. THE BUG: http_server.rs post_message mints reply_to as format!("{this_device}/{from_agent}") unconditionally, with no separator check, and from_agent is only trimmed and emptiness-filtered where it is read. So a caller passing from_agent="CHROME/what-is-next" gets reply_to="CHROME/CHROME/what-is-next", which the far side then refuses. Confirmed end to end on the wire, two consecutive messages from one session to one peer with from_agent the only variable: routing block went CHROME/CHROME/what-is-next then CHROME/what-is-next, and the claim header's agent went "CHROME/what-is-next" then "what-is-next" - two independent signals corrected by one field. DO NOT CHANGE THE RECEIVER: sync.rs passes reply_to: env.reply_to.as_deref(), carrying the value rather than deriving it, and that is deliberate - from_id lowercases and collapses to [a-z0-9-] while resolve_message_target compares exactly, so a receiver reconstructing the address would produce a confident wrong one. WHY THE MISTAKE IS INVITED: GET /api/agents returns two formats under one key. agent_roster sets id: s.id.clone() raw, so a local row is the bare project ("what-is-next") and a remote row is namespaced ("AIR/what-is-next"), while the stripped project is computed beside it and used elsewhere. Looking yourself up in another machine's view of the roster - the natural way to learn what to call yourself - therefore hands you the qualified form, and target IS namespaced while from_agent is NOT. The asymmetry is invisible until a reply bounces. WHY IT COST SO MUCH: an unroutable address and an absent session both land on InboxLookup::NotFound, so both answer 404 no_such_session with the identical sentence "no live interactive session on this machine derives that project id". Four failed sends and two wrong statements to Oleg that a live session had ended, when it had been up throughout; three sessions concluded the other machine's relay was at fault before anyone read http_server.rs. One correction to the report as received: ambiguous_target is already distinct - sync.rs answers it 409 with its own wording about several sessions sharing a directory - so the conflation to fix is specifically unroutable-versus-absent inside no_such_session, not a three-way tie. FIXES, ranked: (1) refuse a from_agent containing "/" with a receipt naming the bare form, since the caller is on the same machine and the correction can be immediate and specific; (2) stop labelling two shapes "id" in /api/agents, or add an explicit self_id so a session never infers its own name from a peer's view; (3) split the refusal reasons so an unroutable address does not read as a dead peer - same-wording-different-cause is what turned a one-character mistake into a wrong diagnosis twice; (4) change nothing in the receiver. Ambiguity has no disambiguator either: with two live sessions in one directory the relay refuses to pick and offers no ref syntax, so both "project [ref]" and "project#ref" fail.

STATUS 2026-09-29 — three of the four fixes are in; THIS MEMO STAYS OPEN FOR FIX (2), which is the root cause and the only one that stops the mistake being invited in the first place.

- **(1) done, by a different remedy than this memo proposed.** Refusing a `from_agent` containing `/` was put to Oleg against two alternatives and he chose to strip and deliver instead: `peer_message::bare_project_id` removes a leading `{this_device}/` (case-insensitively, repeats included) before the mint, so the message still goes and a `warn` records both forms. Another device's prefix is deliberately left alone — `AIR/x` from CHROME is a different error and rewriting it would hide it. The routing block now also names the form it wants, which is where the caller who gets it wrong is by construction.
- **(3) done, and on BOTH routes.** `session_launcher::project_knowledge` answers `Known`/`Unknown`/`Unreadable` over `~/.claude.json`; `sync.rs` splits the receiving side's `no_such_session`, and `StartRefusal::NoSuchProject` splits the same-device route, which a sibling session found still conflated after the first half shipped — one slug `unknown_project` across both, since a caller must not need to know which route it hit. `Unreadable` is a third answer rather than folded into `Unknown`: our failure to read our own file must not become a claim about the caller's address.
- **(4) respected.** The receiver still carries `reply_to` rather than deriving it; nothing in `sync.rs`'s ingest changed.
- **(2) NOT DONE — this is the remainder.** `agent_roster` still sets `id: s.id.clone()` raw, so a local row is the bare project and a remote row is namespaced, both under one key. An agent that learns its own name by looking itself up in a peer's roster — the natural way — still gets the qualified form, which is the thing that produced the doubled address. The symptom is now self-correcting and the refusal is now honest, so this is no longer urgent, and that is exactly why it would otherwise be forgotten. NEXT STEP: decide between renaming the two shapes apart and adding an explicit `self_id` to the roster response. Either is a wire change to a documented route (`docs/pages/development/http-api.md`), so it wants its own decision rather than being folded into a fix.
