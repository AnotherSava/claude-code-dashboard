# Carry the initiating agent's current task on the relay envelope, and store it on the row

User's idea, 2026-09-30, refined in the same conversation. Closes the gap that [[a-subagent-permission-prompt-can-invent-a-row-that-pings-you]] and [[a-relayed-peer-message-becomes-the-receiving-row-s-label-a]] each hit from one side: one row has no text to show, the other has the whole relay envelope as its text. Both are "an agent initiated this work, so use what that agent supplied" — and for the relay case the supplying is already half-built.

WHAT EXISTS. `MessageEnvelope.from_label` (`sync.rs`) is plumbed end to end: `POST /api/message` accepts it (`http_server.rs`, the `from_label` field on the request), it rides `send_message_hop`, and `skills/shared/peer_relay.py` has a `--label` flag that sends it.

WHAT IS MISSING, and it is the whole point. Its only consumer is `peer_message::build_content`, which interpolates it into the message body as `Sender's own description: {l}`. Nothing stores it. So the receiving dashboard, which *built* that string, can only get the fact back by parsing its own prose out again — which is exactly the parse-and-guess this avoids. Two lesser problems on top: the `peer` skill documents `--label` as "<who you are>", so what it carries today is identity rather than the current task, and it is optional, so most sends omit it.

THE CHANGE, three touch points:

1. **The sending dashboard fills it, not the calling agent — but it cannot claim to have observed whose task it is.** Corrected 2026-09-30 against the code: `post_message` does *not* resolve the sender's row. The `from_agent` field is caller-supplied, trimmed, defaulted to `"unknown"` and normalized by `bare_project_id`, and `log_send` writes that string straight into the log line's `chat_id` without ever consulting `AppState`. So stamping the row's `original_prompt` means looking a row up by an id the caller chose, and what it buys is an observed *task text* hanging off a *claimed* identity — the same two-halves-of-unequal-strength problem `build_content` already states for the sender, and which `tailnet::attest` settles for the device half only. The `reply_to` precedent does not rescue it: that is minted from the same `from_agent`, and `bare_project_id` exists because a caller got the field wrong in production (`CHROME/CHROME/what-is-next`, four sends lost). Write it as the sender's claim, corroborated where the dashboard can corroborate it, and do not word it as an observation.

2. **The receiver stores it on the row** rather than only rendering it. That is what lets the row's label and any notification say what the initiating agent was doing, with no parsing.

3. **Keep rendering it in the body too.** The receiving model still benefits from reading it, and `header_safe` already redacts it against the trust vocabulary. Storing it is an addition, not a move.

DECIDE WHILE BUILDING: whether a caller-supplied `from_label` still wins over the dashboard-stamped one (an agent may have a better description of *why* it is messaging than its own prompt gives), or whether the two become separate fields — the caller's "why I am writing" against the dashboard's "what I am doing". The second is more honest and is one more field; the first is cheaper and has to pick a precedence. Not settled here.

ORDERING against [[route-local-agent-messages-through-the-dashboard-by]], asked 2026-09-30. That memo resolves the process owning the loopback connection and maps it to a session, which is exactly what turns the claimed half of touch point 1 into an observed one — and this would be the first feature to consume the *agent* half of a sender identity, the half CLAUDE.md names as the one nothing checks, so it is what makes that gap cost something. It is still not a prerequisite: the gap here is that nothing *stores* `from_label`, and storing a claim beats storing nothing, so this can ship first and the attestation upgrades its provenance afterwards without changing what rides the envelope — the way `tailnet::attest` upgraded the device half. Two conditions on going first. Word the field as a claim from the outset, or the upgrade turns into a redesign of everything that reads it. And expect the local route to become a second caller of the same stamping, which is additive rather than a rework, since both paths enter through `post_message`. Against it: that memo's own Check section leaves two problems open (a pid ambiguous across sessions sharing a cwd, and an ancestor walk past hook subprocesses to the claude image), it forks per platform, and its actual motivation is queuing local messages rather than labels — it sits with the queue memos, so its priority tracks that line of work, not this one.

OUT OF SCOPE, and worth saying because it looks adjacent: this does nothing for the subagent-invented row, whose initiator is a subagent on this machine rather than a peer, and which has no envelope at all. That row's text has to come from `agent-<agent_id>.jsonl`, which is the other memo's third fix.
