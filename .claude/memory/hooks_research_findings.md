Live research (2026-06, extended 2026-09 for subagent permission prompts) on Claude Code hooks for the dashboard's state derivation, validated against the installed binary's Zod schemas (the authoritative source for payload shapes — the public docs don't render the `Stop` JSON example).

**Adopted** (the `Stop` payload superseded transcript workarounds — verified field shapes from the 2.1.195 binary):
- `Stop.last_assistant_message` (string, since 2.1.47) — "Text content of the last assistant message before stopping. Avoids the need to read and parse the transcript file." The adapter's `classify_stop` runs `question_reason` on it directly, so the old too-early-`Stop` correction machinery (`flushed_turn_verdict` + `promote_done_to_blocked`/`demote_scanned_blocked_to_done` + the `status_from_transcript_scan` flag) was deleted.
- `Stop.background_tasks` (optional array of `{id,type,status,description}`, since 2.1.145) — "Empty array when nothing is in flight." Non-empty ⇒ the `Waiting` state, set at `Stop` time; replaced the `pendingBackgroundAgentCount` transcript scrape. `infer_state` now skips sidechain entries for state so background work can't flip a `Waiting` row to `Working`.
- `SubagentStop` (2026-09-25, 2.1.281 binary) — input `{agent_id, agent_transcript_path, agent_type, last_assistant_message?, background_tasks?}`; `agent_transcript_path` honours `agentTranscriptSubdirs`, so a workflow agent's includes `workflows/<run>/`. `runAgent` fires it on a normal end **and** from `finally` ("SubagentStop on interrupted query"), which makes it the only per-agent exit for an aborted subagent that wrote no `tool_result`. Subscribed for that alone: it settles the agent's open permission prompts (`subagent_gate.rs`); the primary release is the gated call's `tool_result` in `agent-<agent_id>.jsonl`, written for every outcome (approved and run, user reject, the 120s safety-check timeout, abort). It **does fire for Workflow agents**: on 2026-09-25 the untagged `subagent stop received` debug line in `widget.jsonl` logged 11 in two minutes from one workflow's agents, whose transcripts sat under `subagents/workflows/wf_*/`.

**Rejected — do not re-propose** (each investigated and ruled out):
- `Notification(idle_prompt)` is now **ignored entirely** (the adapter's Notification arm returns `None` for it). It's a flaky ~60s fixed timer — not state-aware, fires after every response, sometimes never, **never for AskUserQuestion** — so it isn't a usable idle/cancel signal, and once `Stop` became authoritative (last_assistant_message) its transcript re-scan was pure redundancy (removed `classify_turn_end` + `last_assistant_text`). (The Windows `idle_probe` screen-scrape it once corroborated was itself **removed** 2026-07-01 — instant Esc-cancels DO write the `[Request interrupted by user]` marker, so `log_watcher`'s marker path is the authoritative cross-platform cancel detector.) See [[terminal_promote_to_working_unsafe]], [[idle_probe_screen_criteria_tui_sensitive]].
- `PostToolUse`/`PostToolBatch` as a "turn alive" heartbeat — reintegrates the per-Bash/Read/Grep fork+POST overhead the `PreToolUse` matcher-gate avoids, and can't cover the start-of-turn / text-only windows `WORKING_GRACE_MS` + spinner detection handle.
- `MessageDisplay` as busy corroboration — redundant with `WORKING_GRACE_MS`, display-only with a 10s timeout that blocks TUI rendering, and doesn't fire for tool-first turns.
- `MessageDisplay` to **hide the canary marker from the terminal** (2026-07-23) — rejected. It *can* rewrite on-screen text via `hookSpecificOutput.displayContent` **display-only** and it would NOT break the canary read (the transcript + `what Claude sees` keep the original, and `Stop.last_assistant_message` reads the transcript, so the marker stays checkable every turn). BUT the compiled `claude.exe` Zod schema is authoritative and damning: `displayContent:A.string().describe("Text displayed in place of **the delta**")` — MessageDisplay fires **per streaming delta (chunk), not per whole message**. A trailing marker spans token-boundary deltas, so a stateless per-delta hook can't match/strip it and can't know which delta is last; plus it forks synchronously per chunk (the 10s TUI-blocking timeout above). Conclusion: **the visible marker is unavoidable** — no settings/env/output-style/hook hides it. Keep the inline-compact placement (`http_server::session_start_nonce` instruction); zero-width is the only true-invisible route and carries false-drift risk (rejected per [[feedback_indicator_certainty]]). Verified against docs (code.claude.com/docs/en/hooks) + `claude.exe` strings. A whole-message (not per-delta) display-rewrite hook is the missing primitive → `/feedback`.
- `Notification(permission_prompt)` is now **ignored entirely** (2026-09-25). It echoes a `PermissionRequest`: in `widget.jsonl` all 546 `permission_prompt` notifications followed a `PermissionRequest` for the same row 5.4–30.0s earlier, and every one relabelled the row "needs approval: <tool>" from message text. It carries no `agent_id` even when a subagent raised the dialog, so applying it would re-raise a BLOCK the subagent release had just cleared. An echo guard was rejected — it is a timer covering for a duplicate. Residual: a dialog that fired `permission_prompt` with no `PermissionRequest` would show no BLOCK (0 of the 546 did).
- `PostToolUse` / `PostToolUseFailure` / `PostToolBatch` / `PermissionDenied` as the **release signal for a subagent's permission dialog** (2026-09-25). `PermissionDenied` runs only for the auto-mode classifier (`executePermissionDeniedHooks` is gated on `decisionReason.type==="classifier" && classifier==="auto-mode"`, verified in the 2.1.281 binary), and a timeout is a `permission-rule` denial, so it never fires for the case that mattered. `PostToolUse`/`PostToolUseFailure` run only around `tool.call`, so a denied or timed-out call reaches neither, and `PostToolBatch` is skipped on abort (read from the binary during the design review, not re-checked since). All of them also re-add the per-tool fork cost above.
- **No hook payload carries token/context-usage data** (the `effort` field is a level, not tokens) — context-usage % must keep coming from the transcript + OAuth poller.

**`agent_id` marks a subagent's event, but only where the hook builder passes the tool context** (2026-09-25, 2.1.281 binary): the hook input builder sets `transcript_path` to the **main** transcript and `agent_id: s?.agentId`. `executePermissionRequestHooks` passes the tool context, so a subagent's `PermissionRequest` carries its `agent_id` (the adapter also reads `agent_type` when present, for the log); `Notification`, `Elicitation`/`ElicitationResult` and `PreCompact` do not, so a subagent's instance of those is indistinguishable from the main agent's and lands on the main row. An absent `agent_id` therefore means the main agent only on `PermissionRequest`/`PreToolUse`; on the other events it says nothing. `PermissionRequest` input is `{tool_name, tool_input, permission_suggestions?, mcp_server?}` — **no `tool_use_id`**, so `subagent_gate::gate_verdict` finds the gated call by exact input among eligible same-name calls first, and only with no exact match by recency; whether the hook's `tool_input` ever equals the transcript's input is unverified (`matched_on` on `subagent_prompt_settled` measures it). Subagent transcripts live at `<transcript_path minus .jsonl>/subagents/[workflows/wf_*/]agent-<id>.jsonl`, entries tagged `agentId` + `isSidechain: true`; an assistant message is written one entry per content block, all sharing `message.id`, a sibling's `tool_result` can land before the message's next `tool_use` entry, and results can appear out of timestamp order. In each of the five 2026-09-25 incidents the `tool_use` was on disk 0.38–0.57s before the hook arrived, and the result was an `is_error` 120s-timeout denial (`toolDenialKind: "permission-rule"`) 120.25–120.31s later.

**The `ElicitationResult` unblock path is unexercised, not proven** (2026-09-02): three months of captured hook payloads on the Windows box logged 58 `PermissionRequest` and 55 `StopFailure` and **zero** `Elicitation`, so the adapter arm CLAUDE.md calls the authoritative unblock — resuming `Working` when the user answers an MCP prompt — has almost certainly never executed. If a `Blocked` row ever fails to resume after an MCP prompt, suspect that path itself before hunting a regression. Also why it could not have run: until 2026-09-25 the live `~/.claude/settings.json` never subscribed `ElicitationResult` at all (the setup snippet listed it); a synthetic event through the hook then classified `Working` as designed.

**SessionEnd is unreliable on exit → liveness-reaper backstop** (2026-06-29): `SessionEnd` fires cleanly on `/clear` (matcher `clear`) but **not reliably on `exit` / Ctrl-D / terminal close** — it may not fire at all, and even when it does it runs after teardown begins and is killed before an async localhost POST completes (GitHub anthropics/claude-code #69750, #41577). A session quit mid-turn therefore strands its dashboard row (often in `Working`). **No hook payload field or env var exposes the owning Claude PID** either (only `session_id`/`transcript_path`/`cwd`/`effort`/`permission_mode`). Fix: the hook resolves `agent_pid` itself (nearest ancestor whose image is `claude`/`claude.exe`, fresh per event) and `liveness_reaper.rs` removes a row once that pid is image-confirmed dead (Toolhelp32 snapshot, not `OpenProcess` — sidesteps the access-denied + `STILL_ACTIVE` traps). Don't rely on `SessionEnd` as the sole row-removal signal. See CLAUDE.md `liveness.rs`/`liveness_reaper.rs`.

**`SessionStart` / `UserPromptSubmit` inject context via `hookSpecificOutput.additionalContext`** (verified 2026-07 against code.claude.com/docs/en/hooks): a hook that exits 0 and prints `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}` to stdout gets that string added to the model's context — for `SessionStart` once "at the start of the conversation, before the first prompt", for `UserPromptSubmit` "alongside the submitted prompt" every turn. The instruction-adherence canary uses it: the backend mints a per-session nonce, returns it in the `/api/event` response, and the hook echoes it as `SessionStart` additionalContext so the agent ends each reply with a hidden marker. `SessionStart`-only (not per-turn) is deliberate — the injected instruction ages back into mid-context as the dialog grows, which is exactly where long-conversation instruction-drift bites, so a dropped marker there is the signal. See CLAUDE.md `http_server.rs` (canary) + `nonce_store.rs`.

**Policy:** target only the latest Claude Code; no fallbacks for older versions (now in CLAUDE.md `## Conventions`). [[feedback_favor_clean_design]]
