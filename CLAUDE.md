# claude-code-dashboard

Tauri v2 desktop dashboard application.

## Conventions

**Target only the latest Claude Code release.** The dashboard assumes the current Claude Code hook payloads and JSONL transcript format; we do **not** maintain compatibility shims or fallbacks for older versions. When a newer Claude Code signal supersedes a transcript-scraping or inference workaround, adopt the authoritative signal and delete the workaround outright rather than keeping both (favor clean design over back-compat). For example, the `Stop` hook's `last_assistant_message` and `background_tasks` payload fields replaced the prior too-early-`Stop` transcript-correction machinery and the `pendingBackgroundAgentCount` scrape. (Baseline at adoption: Claude Code 2.1.195.)

## Project

An always-on-top desktop widget (Windows + macOS) that tracks live status of AI coding agents. A Rust backend (`src-tauri/`) hosts the Tauri v2 app, an embedded `axum` HTTP server on `127.0.0.1:9077` that accepts status POSTs from external agents, a `notify`-backed transcript watcher that tails Claude Code JSONL for live token updates, and a system tray. A Svelte 5 + Vite frontend (`src/`) renders the session list and subscribes to Tauri events for live updates. A thin Python hook (`integrations/claude_hook.py`) forwards Claude Code's raw lifecycle payload to the HTTP API; all classification / chat-id derivation / transcript question-detection lives in `src-tauri/src/adapters/claude.rs`. The `PreToolUse` hook is matcher-gated to `AskUserQuestion`/`ExitPlanMode` only — Claude Code buffers those user-gating tool_use blocks until the user answers, so the JSONL transcript can't carry that signal in flight and `PreToolUse` is the only way to catch them on screen. (`PermissionRequest` and `Elicitation` mark `Blocked` for the other blocked-on-user cases — tool-permission dialogs and MCP input prompts; `ElicitationResult` is the authoritative unblock that resumes `Working` the moment the user answers the MCP prompt, rather than waiting for the watcher to infer the resume from the transcript.) The adapter also handles `UserPromptExpansion` (the early signal a slash command fires before its `!` context-gathering, so a skill launch shows `Working` at once rather than waiting for the lagging `UserPromptSubmit`), `StopFailure` (an API-error turn fires no `Stop`, so this marks the row `Error` with the failure kind), and `PreCompact` (context compaction → a history separator via the new `AdapterOutput::Boundary`). Runtime state lives at `%APPDATA%\com.anothersava.claude-code-dashboard\` (`config.json` for settings, `widget.jsonl` for tracing output).

Key module map in `src-tauri/src/`: `state.rs` (sticky-label state machine + `mark_session_boundary` for mid-session boundary marking), `config.rs` (load/save), `config_watcher.rs` (notify-backed hot-reload), `http_server.rs` (axum handler; the instruction-adherence canary (`Config::instruction_canary_enabled`, off by default) is orchestrated here: on `SessionStart` it mints a per-session nonce via the managed `nonce_store::NonceStore` (fresh on `startup`/`clear`, but *reused* on `resume`/`compact` — those keep the model's prior context and its original marker instruction, so minting there would inject a second, conflicting marker the model won't adopt, stranding the row Pending; `http_server::session_start_nonce`) and returns the end-of-reply marker instruction in the `/api/event` response body (200 + `EventResponse.additional_context`) for the hook to inject as SessionStart `additionalContext`, on `Stop` it stamps the orthogonal `AgentSession.instruction_drift` flag via `state::set_drift` when `last_assistant_message` lacks the session's current marker (`adapters::claude::marker_for`) — but only once the marker has been observed at least once (`NonceStore`'s `seen` bit), so a lost `SessionStart` response that never delivered the instruction can't false-flag ("starts to skip" semantics), and only on a settled *completion* turn: the pure `http_server::drift_action` returns `Hold` (leave the flag untouched, re-judge next turn) rather than `Confirm` when the dropped-marker turn is a `Blocked` *handback* (`state::status_of`), because a model mid-skill-workflow — canonically a `/commit` reflection ending on a question — legitimately drops the hidden marker there and resumes emitting it on the next normal turn, so confirming a handback drop would false-alarm (logged `deferred=true` on the `drift_check` line; `state::drift_confirmed` reports the held value). A genuine persistent drift still confirms the moment the agent produces a completion turn still missing the marker — at most one completion-turn later. On `Clear` it removes the row via the shared `commands::remove_session` → `AppState::take_session`, which atomically appends a boundary separator, persists, and drops the row, so the next `SessionStart` restores a dialog ending with the separator and the upcoming `UserPromptSubmit` lands after it — Claude `/clear` fires `SessionEnd`+`SessionStart` so the same cwd-derived chat_id is recreated with the prior dialog restored. `remove_session` is shared with the liveness reaper so the SessionEnd path and the exited-without-SessionEnd path can't diverge. The removal is gated by the pure `http_server::clear_permitted`: a chat_id is cwd-derived, so **every** Claude Code instance in that directory addresses the same row, and a `--fork-session --resume` migration (a terminal session forked into a background/desktop one) routinely leaves two resident. The row's owner is the `agent_pid` of whichever instance wrote it last (`liveness::AgentPids`, already overwrite-per-event), so an end signal whose pid differs is refused and logged `decision = "clear_ignored"` rather than flushing and dropping a row a live sibling still holds. Refused only when both pids are known and differ — an unresolvable pid (node-based install) or an empty store after a restart means ownership is unknown, and the authoritative end signal wins. Deliberately *not* solved by splitting the row per instance: a fork is one continuous conversation the user migrated on purpose, and a second row would tear it in half. An `AdapterOutput::Boundary` arm (from `PreCompact`) appends the same separator without ending the session and clears the row's stale `input_tokens` (watcher-only, not rewritten until the next turn) so the context gauge/alert/terminal-title suffix drop on compact instead of freezing at the pre-compact value until the user's next prompt. `SessionEnd` (clear) and `PreCompact` (compact) are the authoritative boundary signals — the prior defensive `transcript_path`-rotation check and the dormant `>50%`-token-drop inference (`state.rs is_new_session`, never fired since the hook path carries no `input_tokens`) were both removed in favor of them), `log_watcher.rs` (transcript tailing + merge policy + watcher-driven Assistant dialog text upsert — the dialog text still comes from the watcher because Claude Code's `Stop` hook fires before the final assistant turn is flushed to JSONL, so the post-`Stop` write the `notify` watcher catches is what fills it in. The question-vs-done *verdict* no longer needs the transcript, though: `Stop` carries the final text as `last_assistant_message` ("avoids the need to read and parse the transcript file") and in-flight background work as `background_tasks` (an array, empty/absent when nothing is running), so the adapter's `classify_stop` settles the row authoritatively at `Stop` time — `Blocked "has a question"` (a hand-back), else `Waiting` (background work still running), else `Done` — and the old too-early-`Stop` correction machinery (a `flushed_turn_verdict` pass plus the `promote_done_to_blocked`/`demote_scanned_blocked_to_done` state corrections and the `status_from_transcript_scan` provenance flag) is gone. `apply_watcher_update` is now purely a promote *to* `Working` (carry a paused row back when the transcript shows the main turn resumed — e.g. the user answered an `AskUserQuestion`); it never demotes, and `infer_state` skips `system` and sidechain entries when resolving state, so background-agent (sidechain) activity can't flip a `Waiting` row back to `Working`. It rested on the premise that an *instant* Esc-cancel (submit, then cancel before any output) writes nothing to the transcript and fires no hook; real transcripts disprove the first half — Claude Code writes `[Request interrupted by user]` even for sub-second, zero-output cancels — so the marker path is the **sole, cross-platform Esc-cancel detector** (adopt the authoritative signal, delete the workaround). Also fires a one-shot `limit_reset` Telegram ping when the account-wide 5h/7d usage window resets after being used past `limit_reset_percent`: `ResetTracker` detects the reset the instant a window's `resets_at` clears to null with its percentage cleared (0 *or* null — the API returns "0/null" in the transient) *and* its own scheduled `resets_at` has arrived (`now + RESET_ARRIVAL_SLACK_MS >= resets_at`, `now` = the snapshot's `updated`) — the prompt path — with a forward-`resets_at`-jump (> `RESET_JUMP_MARGIN_MS`) fallback for coarse polls that skip the `(0, null)` transient and for early rollovers. The arrival gate is what makes the null-drop safe as a prompt signal: a 5h reset transiently zeroes *both* buckets' percentages (and can null *both* `resets_at`s) for up to ~40min, so a bare null-drop can't distinguish a real reset from collateral — but the collateral bucket's own scheduled reset is still hours/days out, so it fails the gate and falls through to the jump path (which is immune to the ±1min `resets_at` jitter). A cleared `resets_at` while the percentage is still a live positive value contradicts a reset, so the prompt path holds fire on it. After a prompt fire, the window's `resets_at` recovery is consumed silently (`awaiting_recovery`) so one reset never pings twice. `ResetTracker` tracks each window's `peak_pct` high-water mark for the threshold test, and buffers the point-event send for per-tick retry (it never auto-deletes, unlike the two reconcilers); the tracker re-seeds on a creds change so a reset during a Telegram-disabled gap can't fire a stale ping on re-enable), `idle.rs` (system-wide input-idle ms via `GetLastInputInfo` on Windows / `CGEventSourceSecondsSinceLastEventType` on macOS, raw FFI like `auto_resize`/`terminal_title`; `None` on query failure or unsupported platform → reconciler treats presence as unknown and skips the AFK path), `prompt_history.rs` (disk persistence for per-session dialog + original_prompt + task_started_at — loads/saves `prompt_history.json` in app data dir. Lives in its own file rather than `config.json` so it survives the deploy step that overwrites config.json), `telegram.rs` (reqwest-based Telegram Bot API client), `terminal_title.rs` (mirrors each session's status onto its terminal tab title as "<colored circle> <name>", with a ` [N%]` context-usage suffix appended by the pure `build_title` once the session crosses `config.terminal_title_context_percent` (default 50; reuses `notifications::context_percent`, so the number tracks the token counter and falls off on a new task/`/clear`); the hook reports candidate pids as `console_pids` in the POST body — console process list + ancestor chain on Windows, ancestor chain alone on macOS, in both cases **bounded at the hook's own Claude Code process** (the `agent_pid` image test), because Claude Code detaches every child it spawns from the controlling terminal, so the whole hook-side subtree of a *desktop-app* session reads `??` and an unbounded walk climbs out of the session and titles whichever terminal happened to launch it — one agent's status overwriting a neighbour's tab every reassert cycle. Bounded, an all-tty-less chain correctly writes nothing: a session with no terminal has no tab to title. A node-based install matches no claude image, so its chain stays unbounded — and `sync` — called inside `commands::emit_sessions_updated`, which every state transition already flows through — pushes the title per platform. Windows: the FreeConsole→AttachConsole→SetConsoleTitleW dance, candidates tried far-to-near because hooks are spawned CREATE_NO_WINDOW into a fresh *invisible* console — the transient near-end pids hold that console while the far end fails attach (GUI ancestors) until the first success lands on the user's real terminal (GetConsoleWindow can't discriminate instead: conPTY consoles report no window on current Win11). macOS: resolve a candidate's controlling tty via `ps -o tty=` and write an OSC 0 escape to `/dev/ttysNNN`, near-to-far since dead transients fail the lookup and Claude's detached hook-side children report no tty, leaving Claude Code itself — the chain's bound — as the tty-bearing candidate. Successive pid reports are intersected so per-hook transient cmd/python pids drop out and only long-lived ones (Claude itself, the user's shell) survive pid reuse; gated by the `terminal_titles` config toggle, and blank-title cleanup on session disappearance is centralized in `sync` rather than at the Clear call site), `sync.rs` (multi-device session sync — single-writer model, **push notifies / pull moves content**: each device pushes a full metadata snapshot of its *local* sessions to `config.sync.peers` (debounced 300ms via the `SyncDirty` Notify poked in `emit_sessions_updated`, plus a 30s heartbeat) with each session's dialog reduced to a `dialog_tip` and the usage timeline to a `usage_tip` — no content on the wire. The receiver compares each tip against what it actually holds and pulls the difference itself (`GET /api/sync/dialog?id=&since=`, `GET /api/sync/usage?since=`), merging via the shared `state::merge_dialog_entries` / `RemoteUsageStore::merge_device`. That split is the design: change events originate at the sender so *notification* must be pushed (polling a live widget would cost several requests a second), but only the receiver knows what it holds, so *content* is requested. The sender is therefore stateless — the same body goes to every peer every cycle, a failed push costs only a retry, and the per-peer/per-session watermark that used to track "how far I think you got" is gone. That watermark was a guess about another device's contents and went stale silently: it was per-peer while the receiver's contiguity check was per-session, so a busy session dragged it past a quiet one's newest held entry and every later delta for the quiet session was discarded (201 such discards in one real log); a discarded delta was acknowledged 204 all the same, so the sender advanced past content that was never stored. The `since` is now derived from the stored entries at the moment of asking, so it cannot drift, and a dropped fetch self-corrects — nothing recorded that the range arrived, the next push re-advertises the same tip, and it is asked for again. Receiver stores into `AppState::remote` — separate from `sessions`, so notifications/persistence/terminal-titles stay remote-blind by construction — with ids namespaced `{device}/{raw_id}` and `origin` stamped; a bearer-token-gated listener on `0.0.0.0:sync.listen_port` serves both pull routes plus the full-dialog catch-up `commands::open_history` triggers for remote targets (bracketed in `history_loading` events the history window renders as a loading hint). That catch-up deliberately asks for *everything* rather than the incremental range: it covers the one case a `since` cannot express — an entry `merge_dialog_entries` dropped as an apparent transcript re-read sits *below* the newest held timestamp. 90s TTL reaper drops silent devices; `resolved_snapshot` is the single local+remote merge point; remote-driven mutations — push ingest, pull merges, TTL reap, dialog catch-up — must emit via `commands::emit_sessions_updated_remote`, which skips the `SyncDirty` poke: a received push poking the pusher echoes the *control signal* even though content can't echo, ping-ponging full snapshots between two devices at the 300ms debounce period), `remote_history.rs` (`RemoteHistoryStore` — disk persistence for remote-device dialogs, one file per device under `remote_history/` in the app data dir; `sync::ingest` re-seeds each session's dialog from it when there's no in-memory predecessor, and `post_sync`/the catch-up save back on new content. Mirrors `prompt_history.rs`, including keep-on-absence), `remote_usage.rs` (`RemoteUsageStore` — disk persistence for remote-device usage-limit samples, one file per device under `remote_usage/`; peers advertise a `usage_tip` on each push and this device pulls the records above what it holds (`GET /api/sync/usage?since=`, range-selected by the pure `sync::usage_since`; `RemoteUsageStore::newest_ts` supplies the `since`, derived from the stored records so it can't drift), `fetch_usage_range` merges them in, and `commands::merged_usage_records` unions every device's records into the Work-intensity chart — the account-wide 5h/7d counter means a peer's polls fill the windows this device's app was closed (`get_usage_intensity_week`/`_weeks` build from the union, not just local). A merge re-emits `usage_limits_updated` so an open intensity window re-fetches live. Mirrors `remote_history.rs`), `usage_limits.rs` (Anthropic OAuth usage poller for 5h / 7d rate-limit bars + direct OAuth refresh; the poll loop is reset-aware via the pure `next_poll_secs` — when a bucket's `resets_at` (5h or 7d) falls within one poll interval, it skips the regular poll and instead wakes `config.usage_reset_poll_delay_seconds` (default 30) after the reset, so the bar refreshes off its stale pre-reset value promptly instead of up to a full interval later, and the pre-reset poll is skipped so the two don't fire close together and trip the endpoint's aggressive 429; the delay clears the ±1min `resets_at` jitter + server propagation, and a reset already passed by more than the delay re-polls at the `MIN_POLL_SECS` floor until the fresh window lands), `usage_history.rs` (`UsageHistoryStore` — append-only `usage_history.jsonl` in the app data dir, one flat record per successful usage poll with raw API percentages + reset times in epoch ms; the data source for the Work intensity window — the pure `build_week_chart` bins it into a `WeekChart` of 10-min intensity buckets (intensity = clamped Δ of `five_hour_pct` between consecutive polls; resets are detected by a pct drop, never by `five_hour_resets_at`, which jitters ±1min without an actual reset — see the `usage_five_hour_resets_at_jitter` memory)), `auto_resize.rs` (Up/Down content-fit window with edge anchor; a cross-platform vertical resize lock (`resize_lock`) that keeps a manual edge drag from fighting the content fit while leaving width to the user — its blind spot, maximizing, is closed one level up by `"maximizable": false` on the main window in `tauri.conf.json`, which drops `WS_MAXIMIZEBOX` so a header drag to the top edge can't snap-maximize and makes Tauri's drag-region double-click (`internal_toggle_maximize`, gated on `is_maximizable()`) inert in the maximize direction only, so an already-maximized window can still be restored; see the `install_resize_lock` doc for why it isn't tied to a fit mode — on Windows a `WM_NCHITTEST`/`WM_NCLBUTTONDOWN` subclass neutralizing the top/bottom/corner hit-tests, on macOS a min == max content-height pin (`set_size_constraints`) rebuilt from the window's `tauri.conf.json` bounds on every apply so the declared `minWidth` survives the four-bounds write, since an undecorated NSWindow keeps `NSWindowStyleMask::Resizable` and stays edge-resizable. `engage` runs *before* the resize, not after: a pin left from the previous apply would otherwise clamp `set_size` back to the old height, and engaging first is the only ordering that holds whether the platform applies the resize inline (Windows) or defers it to the main queue (macOS). A minimize guard (`is_minimized`) fronts `apply`: a minimized window reports the OS's iconic rect rather than its own geometry (on Windows `outer_position` reads (-32000, -32000) and `inner_size` reads SM_CXMINIMIZED x SM_CYMINIMIZED, 237x39 at 144 DPI), so the anchor arithmetic, the work-area clamp (which always resolves to a corner, the iconic rect overlapping no monitor) and the carried-over width are all computed from a rect that isn't the window's — which is how a full-screen game, which minimizes the always-on-top widget, left it collapsed to a header sliver. The same guard fronts `commands::ensure_window_on_screen` (a minimized window is off every monitor by construction, so the off-screen rescue would otherwise fire on every show-while-minimized) and `commands::set_compact_width` (reachable on the usage-poll cadence for as long as the widget stays minimized). It is keyed on minimized and deliberately NOT on visibility: a window hidden to the tray keeps a real rect, and skipping there would bring the widget back stale on every tray toggle. Recovery cannot start in the frontend — minimizing never resizes the WebView2 child, so `window.innerHeight` stays frozen at its pre-minimize value across the whole round trip and every viewport-keyed self-heal (the `vh * 2 < desired` collapse heal included) reads the window as already fitting — so `lib.rs`'s `refit_after_restore` folds `WindowEvent::Resized` (emitted for both edges, and for our own resizes) down to the minimized->restored edge via `resized_is_restore` and emits `refit_window`, which `App.svelte` answers with a dedup-disarmed `forceMeasure`. Inert on macOS, where a miniaturized `NSWindow` keeps its real frame and tao emits no `Resized` on either edge — nothing to corrupt, so nothing to recover. Managing frontend-read state there is a structural fix for the whole class of mount-time `State` races — `get_config` latching `Config::default()` (auto_resize `None` → frozen window), `frontend_log` dropping every early log, `get_setup_state` flashing the onboarding panel — so `.setup()` (which runs later at Ready, after the webviews exist) does only window/tray/service wiring and reads config from the already-managed state, never managing frontend-read state itself. The former `emit_config_updated` / `emit_setup_state` re-pushes and the frontend authoritative re-read were all removed with this fix. On macOS, `lib.rs` setup() calls `app.set_activation_policy(ActivationPolicy::Accessory)` so the app has no Dock icon or menu bar (mirrors the Windows `skipTaskbar` intent). Before the Tauri builder runs, `lib.rs` `clear_webview_cache()` (Windows-only) deletes the WebView2 `EBWebView` cache on every launch: WebView2 caches the fixed-URL `index.html`, so a redeploy/update that only swaps the content-hashed bundle keeps serving stale frontend JS — and the staleness recurs on every launch *within* a single build (so a build-fingerprint gate isn't enough; it must be cleared unconditionally). Must run before window creation because config-defined webviews start loading immediately. The embedded frontend is served from the binary, so the cache buys nothing (see `tauri-webview2-cache-staleness` learning). A second window (label `"history"`, pre-configured hidden in `tauri.conf.json`) shows full dialog history for a session; `HistoryApp.svelte` is its root component. `HistoryTarget` managed state + `history_target` Tauri event pass the session ID from the dashboard click to the history window. `history_font_size` config field (5-step enum) persists font size; tray submenu and Ctrl+/- in the history window both write it. A third window (label `"about"`, decorated + `theme: "Dark"` + `alwaysOnTop` for a float-on-top feel) is the About dialog, surfaced via Help → About; it intentionally does **not** set `parent: "main"` — on macOS NSWindow's `addChildWindow:ordered:` cascades visibility from parent to child, so a parent-child relationship would auto-show About when the main window is first revealed at launch (the App.svelte `aboutMode` gating is sufficient on Windows because Win32 owned windows don't auto-show with their owner, but is insufficient on macOS without removing the parent); `AboutApp.svelte` renders title + version + release date (embedded by `build.rs` via `chrono::Local::now()` in a `cargo:rustc-env`) + clickable docs URL opened in the user's browser via `open::that`. A fourth window (label `"intensity"`, decorated + `theme: "Dark"`) is the Work intensity chart, opened from the tray's **Work intensity** item; `IntensityApp.svelte` is its root — it renders `usage_history` binned by `commands::get_usage_intensity_week`/`get_usage_intensity_weeks` (each → a `WeekChart`; `local_week_start_ms` aligns weeks to local-time Monday 00:00) onto a `<canvas>`, in a **Days** view (7 day-rows, x = time of day) and a scrollable **Weeks** view (one row per week, newest at the bottom, x = Mon→Sun, buckets downsampled ×3); a dashed reference marks the full-5h pace and bars past 2× it clip red. `App.svelte` routes between the four roots via `getWindowLabel()` — the `finally { showWindow() }` block must check **all** non-main mode flags (`!historyMode && !aboutMode && !intensityMode`) or hidden secondaries auto-reveal on every launch. Dynamic `WebviewWindowBuilder` windows were tried first but have broken IPC on Windows — see `tauri-windows-native` learning. All Rust tests live in `#[cfg(test)]` modules next to the code they cover.
