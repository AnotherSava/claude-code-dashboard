# claude-code-dashboard

Tauri v2 desktop dashboard application.

## Conventions

**Target only the latest Claude Code release.** The dashboard assumes the current Claude Code hook payloads and JSONL transcript format; we do **not** maintain compatibility shims or fallbacks for older versions. When a newer Claude Code signal supersedes a transcript-scraping or inference workaround, adopt the authoritative signal and delete the workaround outright rather than keeping both (favor clean design over back-compat). For example, the `Stop` hook's `last_assistant_message` and `background_tasks` payload fields replaced the prior too-early-`Stop` transcript-correction machinery and the `pendingBackgroundAgentCount` scrape. (Baseline at adoption: Claude Code 2.1.195.)

## Project

An always-on-top desktop widget (Windows + macOS) that tracks live status of AI coding agents. A Rust backend (`src-tauri/`) hosts the Tauri v2 app, an embedded `axum` HTTP server on `127.0.0.1:9077` that accepts status POSTs from external agents and serves them a read-only roster of every tracked session, a `notify`-backed transcript watcher that tails Claude Code JSONL for live token updates, and a system tray. A Svelte 5 + Vite frontend (`src/`) renders the session list and subscribes to Tauri events for live updates. A thin Python hook (`integrations/claude_hook.py`) forwards Claude Code's raw lifecycle payload to the HTTP API; all classification / chat-id derivation / transcript question-detection lives in `src-tauri/src/adapters/claude.rs`. The `PreToolUse` hook is matcher-gated to `AskUserQuestion`/`ExitPlanMode` only — Claude Code buffers those user-gating tool_use blocks until the user answers, so the JSONL transcript can't carry that signal in flight and `PreToolUse` is the only way to catch them on screen. (`PermissionRequest` and `Elicitation` mark `Blocked` for the other blocked-on-user cases — tool-permission dialogs and MCP input prompts; `ElicitationResult` is the authoritative unblock that resumes `Working` the moment the user answers the MCP prompt, rather than waiting for the watcher to infer the resume from the transcript.) The adapter also handles `UserPromptExpansion` (the early signal a slash command fires before its `!` context-gathering, so a skill launch shows `Working` at once rather than waiting for the lagging `UserPromptSubmit`), `StopFailure` (an API-error turn fires no `Stop`, so this marks the row `Error` with the failure kind), and `PreCompact` (context compaction → a history separator via the new `AdapterOutput::Boundary`). Runtime state lives at `%APPDATA%\com.anothersava.claude-code-dashboard\` (`config.json` for settings, `widget.jsonl` for tracing output).

Key module map in `src-tauri/src/`: `state.rs` (sticky-label state machine + `mark_session_boundary` for mid-session boundary marking), `config.rs` (load/save), `config_watcher.rs` (notify-backed hot-reload), `http_server.rs` (axum handler; the instruction-adherence canary (`Config::instruction_canary_enabled`, off by default) is orchestrated here: on `SessionStart` it mints a per-session nonce via the managed `nonce_store::NonceStore` (fresh on `startup`/`clear`, but *reused* on `resume`/`compact` — those keep the model's prior context and its original marker instruction, so minting there would inject a second, conflicting marker the model won't adopt, stranding the row Pending; `http_server::session_start_nonce`) and returns the end-of-reply marker instruction in the `/api/event` response body (200 + `EventResponse.additional_context`) for the hook to inject as SessionStart `additionalContext`, on `Stop` it stamps the orthogonal `AgentSession.instruction_drift` flag via `state::set_drift` when `last_assistant_message` lacks the session's current marker (`adapters::claude::marker_for`) — but only once the marker has been observed at least once (`NonceStore`'s `seen` bit), so a lost `SessionStart` response that never delivered the instruction can't false-flag ("starts to skip" semantics), and only on a settled *completion* turn: the pure `http_server::drift_action` returns `Hold` (leave the flag untouched, re-judge next turn) rather than `Confirm` when the dropped-marker turn is a `Blocked` *handback* (`state::status_of`), because a model mid-skill-workflow — canonically a `/commit` reflection ending on a question — legitimately drops the hidden marker there and resumes emitting it on the next normal turn, so confirming a handback drop would false-alarm (logged `deferred=true` on the `drift_check` line; `state::drift_confirmed` reports the held value). A genuine persistent drift still confirms the moment the agent produces a completion turn still missing the marker — at most one completion-turn later. It then forgets the nonce only on a `/clear` `SessionEnd` (`reason == "clear"`, which wipes context; a plain exit/logout keeps it so a later `resume` reuses it); the marker is stripped (`adapters::claude::strip_response_marker`, shared with `log_watcher`'s assistant-text capture, gated on the feature toggle and matching exactly `MARKER_HEX_LEN`=4 hex inside the hardcoded `adapters::claude::CANARY_MARKER` middot wrapper (`·{nonce}·` — no longer a config field; the only canary setting is the on/off `instruction_canary_enabled`) so an incidental hex run of another length or delimiter survives) from classified + stored assistant text, and drift surfaces — status untouched — as the `SessionItem` agent-name color (`AgentSession.canary`: green `Alive` = set up + *confirmed* adhering, amber `Pending` = set up but the marker not yet observed, red `Dead` = drifted, default `Off` = not set up — stamped for local rows in `commands::resolved_snapshot` from the live `nonce_store` (nonce + `seen` bit) + `instruction_drift`; `Alive` requires `seen` so green never over-claims) + a `SessionItem` ⚠ row badge + a `⚠` `terminal_title::build_title` suffix + a `notifications::drift_reconcile` Telegram ping (mirroring the context-usage alert overlay), logged `decision = "drift_check"`/`"drift_alert"`/`"drift_dismiss"`; turning the feature off clears every drift flag via `state::clear_all_drift` in `config_watcher` so the badge + title drop with the ping. On `Clear` it removes the row via the shared `commands::remove_session` → `AppState::take_session`, which atomically appends a boundary separator, persists, and drops the row, so the next `SessionStart` restores a dialog ending with the separator and the upcoming `UserPromptSubmit` lands after it — Claude `/clear` fires `SessionEnd`+`SessionStart` so the same cwd-derived chat_id is recreated with the prior dialog restored. `remove_session` is shared with the liveness reaper so the SessionEnd path and the exited-without-SessionEnd path can't diverge. The removal is gated by the pure `http_server::clear_permitted`: a chat_id is cwd-derived, so **every** Claude Code instance in that directory addresses the same row, and a `--fork-session --resume` migration (a terminal session forked into a background/desktop one) routinely leaves two resident. The row's owner is the `session_id` of whichever instance wrote it last (`ChatIdRegistry::claim`, called on every `Set`; `owner_of`/`disown` read and drop it), so an end signal carrying a different `session_id` is refused and logged `decision = "clear_ignored"` rather than flushing and dropping a row a live sibling still holds. Refused only when the owner is known and differs — nothing claimed since a restart, or a payload without a `session_id`, means ownership is unknown and the authoritative end signal wins. `/clear` still removes its own row: it fires `SessionEnd` under the *old* session_id, which is the one that claimed the row, and mints the new id only on the following `SessionStart`. Ownership is deliberately **not** keyed on the hook's `agent_pid`, which was tried and shipped and failed in production: the hook resolves that pid by walking its ancestors for a live `claude` image, so a session that is *shutting down* reports `null` — precisely when the guard has to hold — and "unknown ownership" waved a real killed-sibling `SessionEnd` straight through. The `session_id` is in the payload unconditionally and needs no live process to read. Deliberately *not* solved by splitting the row per instance: a fork is one continuous conversation the user migrated on purpose, and a second row would tear it in half. An `AdapterOutput::Boundary` arm (from `PreCompact`) appends the same separator without ending the session and clears the row's stale `input_tokens` (watcher-only, not rewritten until the next turn) so the context gauge/alert/terminal-title suffix drop on compact instead of freezing at the pre-compact value until the user's next prompt. `SessionEnd` (clear) and `PreCompact` (compact) are the authoritative boundary signals — the prior defensive `transcript_path`-rotation check and the dormant `>50%`-token-drop inference (`state.rs is_new_session`, never fired since the hook path carries no `input_tokens`) were both removed in favor of them. The same server also answers the read-only `GET /api/agents` — the roster an external agent reads to learn what is running *across* the user's machines, which Claude Code's own local-only session listing structurally cannot tell it. It merges through the very same `commands::resolved_snapshot` (widened to `pub(crate)` for it) the frontend uses, so there is no second merge to drift, and pairs each remote row with its device's `last_seen` (`state::remote_last_seen`, metadata only; freshness lives on the device, not on the session row, so the roster needs a second accessor to reach it) to report a `last_seen_age_ms`. That age is the point of the route: a peer's rows sit frozen at their last-pushed status for the 90–120s until the TTL reaper drops them, so a bare `idle` is otherwise indistinguishable from a dead machine's last words. All the judgment is in the pure `http_server::agent_roster` (prefix-stripped by `origin`, never by splitting on `/`, since a device name may contain one; ages clamped at 0 against sender-clock skew; a remote row whose device was reaped between the two locks is dropped rather than reported ageless). Two things it deliberately does **not** return, both settled and not to be re-added: a `deliverable`/`sendable` boolean (a green light computed from up-to-90s-old data over-claims — return facts, let the caller weigh the age) and user presence / idle-ms (a peer message starts a turn in the receiving agent whether or not a human is watching, so presence changes no decision). It is not a message broker — no queue, no sending, no mutation, and so no `decision` log line, since every existing tag marks a state change the `investigate` skill replays. The roster has a **second session source**: `session_registry::SessionRegistry::live_sessions` (Claude Code's own on-disk list of live local sessions), unioned in by `agent_roster` so a dashboard restart no longer empties the local view — the hook stream teaches it a session exists only when that session emits something, so the roster used to refill on activity rather than on a timer and an idle session stayed invisible for as long as it stayed idle (measured after one redeploy: 9 live sessions, 1 row; six minutes later, 2). Registry sessions are **read-path only** — no `AppState` row, no emit, no persistence, so they reach neither notifications nor terminal titles nor prompt history — and they surface in their own `registry_only` array rather than as a flag on `agents`: the registry's `status` is `idle`/`busy` *only*, which cannot express `Blocked`/`Waiting`/`Error`, so it is reported verbatim as a differently-named `activity` field (`Activity::{Idle,Busy,Unknown}`) that no caller can mistake for a `Status`, and a hook-derived row wins every id collision. That precedence is keyed on **`(device, project)`, not the bare id**: a peer's registry rows now ride the sync push (`SyncPush::registry_sessions`, `serde(default)` so an older peer parses and contributes nothing; stored on `RemoteDevice::registry_sessions`), and deduping on the project alone would delete a peer's row because *this* box happens to run the same project — verified live with three projects checked out on both machines. Syncing them closed a gap that was the wrong way round: the union was originally read-path-*local*, so **discovery was narrower than delivery** — a live session on the other machine was absent from the roster while `POST /api/message` reached it perfectly well (it resolves the target in the *receiving* dashboard's registry), so an agent following the documented "check the roster first" concluded the target was gone. The unreadable signal moved with it: `registry_only` is now an always-present `Vec` alongside a `registry_unreadable: Vec<String>` naming the devices that gave no answer, because the old `Option`'s `None` ("this device's registry was unreadable") could not survive an array spanning devices — one unreadable machine would have had to null the whole array and hide every other machine's rows. A peer predating the field lands there too, which is the same fact for the receiver: no answer. A remote registry row's `activity_age_ms` is **skew-free**, unlike `AgentRow::status_age_ms`: the sender ships the age it measured at push time and the receiver adds its own since-the-push elapsed, two durations summed, needing no clock agreement. A `provenance` discriminator on one array was rejected — its only job would be to say which meaning `status`/`label` currently hold — as was making those two fields optional, which would break a caller that reads them per their documented guarantee. The `Origin` guard is per-handler rather than a layer, so every route calls the shared `origin_blocked`. The third route, `POST /api/message`, is the sender-side entry for cross-machine messaging (see `peer_message.rs`): it may live on the unauthenticated loopback server because the *sender* is local, and it is the only route that adds a second gate — a loopback `Host` (`host_is_loopback`) on top of the CSRF check. That reprices the DNS-rebinding gap `origin_blocked`'s doc records as knowingly accepted: accepted for a status write and a roster read, not for a route that starts a turn inside a live agent on another machine. The hook routes keep the gap, since the `TAURI_DASHBOARD_URL` host alias they support is a real setup and their stake is unchanged. Refusals it makes with certainty about the *remote* side are only two — a device it holds no address for, and a live local target (refused with `SendMessage` named, since a relay would destroy the kernel-verified sender identity and the reply address that tool carries); every other question about the far machine, above all whether the project exists over there, is the receiving dashboard's to answer, because this side's roster is at best one push cycle old. A local project with **nothing** running is the one case that decision leaves uncovered rather than settles — `SendMessage` can only address a session that exists — so `TargetResolution::Local` is split into `LocalLive` (refused exactly as before) and `LocalIdle`, which starts a session via `session_launcher::start_and_wait` and then **stands aside**: the receipt is still an `Outcome::Refused`, reason `local_target_started`, because nothing was relayed and nothing will be. The dashboard supplies the capability Claude Code lacks (existence); Claude Code keeps the one it has (delivery under a verified identity). Gated on `sync.accept_messages` like the hop is, since it is the same grant reached by a different door), `log_watcher.rs` (transcript tailing + merge policy + watcher-driven Assistant dialog text upsert — the dialog text still comes from the watcher because Claude Code's `Stop` hook fires before the final assistant turn is flushed to JSONL, so the post-`Stop` write the `notify` watcher catches is what fills it in. The question-vs-done *verdict* no longer needs the transcript, though: `Stop` carries the final text as `last_assistant_message` ("avoids the need to read and parse the transcript file") and in-flight background work as `background_tasks` (an array, empty/absent when nothing is running), so the adapter's `classify_stop` settles the row authoritatively at `Stop` time — `Blocked "has a question"` (a hand-back), else `Waiting` (background work still running), else `Done` — and the old too-early-`Stop` correction machinery (a `flushed_turn_verdict` pass plus the `promote_done_to_blocked`/`demote_scanned_blocked_to_done` state corrections and the `status_from_transcript_scan` provenance flag) is gone. `apply_watcher_update` is now purely a promote *to* `Working` (carry a paused row back when the transcript shows the main turn resumed — e.g. the user answered an `AskUserQuestion`); it never demotes, and `infer_state` skips `system` and sidechain entries when resolving state, so background-agent (sidechain) activity can't flip a `Waiting` row back to `Working`. The `Waiting` state (the "main turn settled but background work — a `shell` task or a subagent — is still running" case, rendered light-blue as WAIT) is entered by `classify_stop` from a non-empty `background_tasks` and left when the next turn's `Stop` reports an empty `background_tasks` and settles `Done` — or, when a user-killed background *shell* task leaves nothing to fire that next `Stop`, settled to `Done` by the `waiting_settle` backstop after `config.waiting_settle_ms` (WAITs with no shell task (subagent, Workflow, …) are excluded from that backstop — see `waiting_settle.rs`). Also detects the `[Request interrupted by user]` marker an Esc-cancel writes — `infer_state` flags it `ended` and `apply_and_emit` calls `state::revert_cancelled_turn` so the row leaves `Working` without a lifecycle hook, reverting to the status it held *before* the cancelled turn (`AgentSession::status_before_working`, captured by `apply_set` on each non-Working→Working transition) rather than blanket `Idle` — so an aborted reply to a pending question lands back on `Blocked` and the user's real answer stays an approval cycle instead of clobbering the task; gated by the `detect_cancelled_turns` config flag), the former `idle_probe.rs` — a Windows-only backstop that read the session's terminal screen and reverted a `Working` row when it positively showed Claude's idle prompt — was **removed** in favor of the `log_watcher` marker path above. It rested on the premise that an *instant* Esc-cancel (submit, then cancel before any output) writes nothing to the transcript and fires no hook; real transcripts disprove the first half — Claude Code writes `[Request interrupted by user]` even for sub-second, zero-output cancels — so the marker path is the **sole, cross-platform Esc-cancel detector** (adopt the authoritative signal, delete the workaround). The screen-scrape was a false-positive-only workaround: a legitimately slow *silent* turn presents the same idle-prompt-over-quiet-transcript picture as an instant cancel, so it could wrongly revert a live turn to `Blocked` — a bug no grace window could fix. `liveness_reaper` still covers cancel-then-`exit`, and the next `UserPromptSubmit` re-classifies any unmarked cancel, `liveness.rs` (process-liveness primitives + the `AgentPids` store. Removal flows through the shared `commands::remove_session`, guarded by `updated` (via `take_session`) to abort the reap-vs-restart race. (The classify reason tallies the tasks by `type`, so an unrecognized kind is named in the log rather than hidden.) For an armed WAIT it's pure time-in-state via `state_entered_at`, which any real status change resets, so a legitimate finite shell task (tests/CI/builds) self-resolves well within the window (a ~9-min ceiling measured across the transcript history) and is promoted off `Waiting` long before it; only a stuck killed-shell WAIT ages past it. Because `disablesleep` is a system-wide kill switch that also suppresses **thermal-emergency and low-battery sleep**, every hold is bounded. Three *policies* (`config::LidAwakeMode`: `Off`/`OnBattery`/`Always`) govern automatic arming, plus a separate one-shot tray action ("Start now" -> `arm_manual`) that overrides the policy, `Off` included, and is re-anchored to the lid-close edge so it gets the same full window. It is not a policy *value* (a mode meaning only "don't arm automatically" would be indistinguishable from `Off`), but the tray still shows both in one radio group with the check-mark on whatever is actually in effect -- a running hold, else the policy -- plus a countdown label. The route is: a sending agent POSTs to its own dashboard on loopback (`POST /api/message` in `http_server`, which is the only place holding the originating agent's identity, so the `message_id` is minted and the claim attached there) → an authenticated hop to the peer's 9078 (`sync::send_message_hop`, own 20s `MESSAGE_HOP_TIMEOUT_SECS`, not the pusher's fire-and-forget 10s) → the peer resolves the target in **its own** `session_registry`, reads that session's `<pid>.<64hex>.key` as the user who owns it, and writes one `\n`-terminated frame (auth line first on every platform, though only Windows requires it) into its inbox. The obvious shortcut — SSH over, read the far machine's key, inject it into that machine's IPC channel — was tried and **refused by the permission classifier, correctly**: its shape is indistinguishable from exfiltration, so no credential crosses the wire and only the dashboard already running as that user reads a key. **A local target is refused, not brokered** — Claude Code's own `SendMessage` carries a kernel-verified sender identity and a working reply address, both of which a relay destroys, so brokering would hand the caller a worse copy of a tool it has. **The sender's identity has two halves of unequal strength**, stated separately by `build_content` (which replaced `claim_header`): the receiver stamps `verifiedPeerPid` with the *peer dashboard*, so the sender rides inside the body — but the **device** half is now attestable via `tailnet::attest` while the **agent** half is not checkable by anything, this route being loopback and unauthenticated by design. Collapsing both into one UNVERIFIED label (as first shipped) threw away the fact a receiver needs to judge a reply; collapsing them the other way would claim about the agent what was only established about the machine. `build_content` also fences the sender's text between `----- BEGIN/END RELAYED MESSAGE {nonce} -----` markers and puts the routing block **after** it, stating its own precedence — the fix for a real failure on 2026-08-30 where a sender's prose ("your reply cannot come back through this relay automatically") contradicted the dashboard's routing line three lines above it and the receiver had no basis to prefer either; the header ended in `\n\n` with the body concatenated straight on, so the contradiction read as a continuation of the same authority. The fence nonce is minted from `RandomState` (OS-seeded) rather than `DefaultHasher` (SipHash under a zero key, fully predictable) precisely because the sender supplies the text the fence must contain; `RESERVED_PHRASES` extends `header_safe`'s redaction from the trust vocabulary to the routing vocabulary (`/api/message`, `in_reply_to`, `RELAYED MESSAGE`, …). The stated ceiling, not a gap to close: a body can still *claim* anything, since 64KB of free text cannot be stripped of routing language — what the design buys is that the two authorities are distinguishable and one carries an address usable without trusting prose. `MessageEnvelope.reply_to` is **carried, not derived**: `from_id` lowercases and collapses both halves to `[a-z0-9-]` while `resolve_message_target` compares exactly, so `Some-Laptop.local`/`tauri dashboard` do not round-trip and a receiver deriving an address would produce a confident wrong one. It is minted in `http_server::post_message`, the only place holding both exact values; absent a `from_agent` the envelope says there is no reply address rather than printing a broken one. `in_reply_to` is inert — rendered, never branched on — so two overlapping exchanges are distinguishable by the agents. A reply is simply another relayed message addressed at `reply_to`, which starts a turn in the original sender: there is nothing to poll, which is what keeps this async rather than RPC. The frame's `from` is `did:ccdash-{device}-{agent}` because the receiver keys its token bucket / identical-repeat slot / sender LRU on `from:${from}` and falls back to the writing pid only when it is absent, which would collapse every relayed message into one bucket; `did:` is accepted by its address validator and, unlike `uds:`, is never mistaken for a reply address. **The receipt is worded for what was observed** (`Outcome::Written`/`Duplicate`/`Refused`/`Unreachable`/`Unknown`, each with an `observed` sentence on the wire) because a raw writer to a Claude Code inbox distinguishes exactly two states — nothing listening, and a listener accepted our bytes; parse, auth, admission and the delivered/held/refused verdict are all invisible, since drop receipts go out on a *separate connection back to the frame's `from`*, which a relay binding no inbox never receives (probed against a throwaway 2.1.251 session: a well-formed frame and 12s of garbage both produced no readback and no EOF). `Unknown` — the hop's answer was lost — answers **200**, never a 5xx, because a 5xx reads as "retry" and this is the one outcome where retrying writes twice. Idempotency is the receiving dashboard's `MessageDedupe`, keyed `(origin_device, message_id)` with a 10min window and cap-and-clear bounding (mirroring `sync::reject_log_due`), claimed *before* the write and released when the write fails; Claude Code's own 30s repeat drop is deliberately not leaned on, being `lastBody`-only, remotely tunable to 0, and invisible to us. Logged `peer_send` (9077 entry, keyed by the *sender's* chat_id since `investigate.py`'s `agent_of` needs one), `peer_relay` (the hop), `peer_write` (the socket write, keyed by the receiving row), `peer_refused` — never the body, never a token. The Windows leg is written from the record's `messagingSocketPath` rather than constructed and was **verified Mac → Windows on 2026-08-30**, closing the three questions that had been open: the Windows build does write the session registry, it does publish `messagingSocketPath`, and its pipe accepts the same auth-line-first `\n`-terminated frame — the receiving agent surfaced the message in its transcript, and the receiving dashboard logged `peer_write` with `authenticated = true` and `outcome = "written"`. Windows → Mac was exercised on 2026-08-31: a reply from that session arrived correlating on `in_reply_to`, so both directions have now been observed. The pipe path confirms the `LOCAL\` segment (`\\.\pipe\LOCAL\cc-msg-<32hex>`) that the client's own validator regex does not imply. The silent-close caveat is unchanged and platform-independent: a bad first line is closed with no error, so `written` still reports only that a listener accepted our bytes, and one observed end-to-end delivery does not upgrade it into a receipt), `remote_history.rs` (`RemoteHistoryStore` — disk persistence for remote-device dialogs, one file per device under `remote_history/` in the app data dir; `sync::ingest` re-seeds each session's dialog from it when there's no in-memory predecessor, and `post_sync`/the catch-up save back on new content. Mirrors `prompt_history.rs`, including keep-on-absence), `remote_usage.rs` (`RemoteUsageStore` — disk persistence for remote-device usage-limit samples, one file per device under `remote_usage/`; peers advertise a `usage_tip` on each push and this device pulls the records above what it holds (`GET /api/sync/usage?since=`, range-selected by the pure `sync::usage_since`; `RemoteUsageStore::newest_ts` supplies the `since`, derived from the stored records so it can't drift), `fetch_usage_range` merges them in, and `commands::merged_usage_records` unions every device's records into the Work-intensity chart — the account-wide 5h/7d counter means a peer's polls fill the windows this device's app was closed (`get_usage_intensity_week`/`_weeks` build from the union, not just local). A merge re-emits `usage_limits_updated` so an open intensity window re-fetches live. Mirrors `remote_history.rs`), `usage_limits.rs` (Anthropic OAuth usage poller for 5h / 7d rate-limit bars + direct OAuth refresh; the poll loop is reset-aware via the pure `next_poll_secs` — when a bucket's `resets_at` (5h or 7d) falls within one poll interval, it skips the regular poll and instead wakes `config.usage_reset_poll_delay_seconds` (default 30) after the reset, so the bar refreshes off its stale pre-reset value promptly instead of up to a full interval later, and the pre-reset poll is skipped so the two don't fire close together and trip the endpoint's aggressive 429; the delay clears the ±1min `resets_at` jitter + server propagation, and a reset already passed by more than the delay re-polls at the `MIN_POLL_SECS` floor until the fresh window lands), `usage_history.rs` (`UsageHistoryStore` — append-only `usage_history.jsonl` in the app data dir, one flat record per successful usage poll with raw API percentages + reset times in epoch ms; the data source for the Work intensity window — the pure `build_week_chart` bins it into a `WeekChart` of 10-min intensity buckets (intensity = clamped Δ of `five_hour_pct` between consecutive polls; resets are detected by a pct drop, never by `five_hour_resets_at`, which jitters ±1min without an actual reset — see the `usage_five_hour_resets_at_jitter` memory)), `token_history.rs` (`TokenHistoryStore` — append-only `token_history.jsonl`, one record per Claude API response keyed by `message.id`, carrying the four token components separately plus a per-device append `seq`; the plan-independent unit for the Work intensity chart's Tokens view, added because the percentage series is denominated in the *plan's* quota and so breaks across a tier change (Max 5x → 20x on 2026-08-27) with no way to recover the past, only percentages having been stored. Three invariants: (a) **components are never pre-weighted at write time** — which ones count as work is a display decision (`TokenRecord::work_tokens` = input + cache_creation + output; `cache_read` is stored but excluded, being 97.1% of the raw sum and a proxy for conversation length, correlating with the account 5h counter at ρ=0.44 vs 0.80 for the chosen combination) and the source self-deletes in ~30 days, so collapsing it early would repeat exactly the mistake above; (b) **`reduce_by_id` takes the max per field per id, applied at every read** — Claude Code writes one transcript line per *content block*, each repeating the whole usage object (54.98% duplicate ids measured; naive summing inflates totals 2.03x), and max-per-field is idempotent/commutative/associative, which is what makes a re-scan, a late fan-out line, an out-of-order pull and an overlapping range all harmless by construction rather than by discipline; (c) **`seq` is the transport clock and `ts` the event clock** — `seq` starts at 1 so 0 is an unambiguous "nothing held" watermark. The pure `build_token_week_chart` is a plain histogram (point events, no interval deltas, so no reset clamp and no gap exclusion) with `has_data` meaning simply "inside the range we hold records for" — transcripts are written by Claude Code itself, so unlike the usage poller a closed dashboard loses nothing and hatching those buckets would hide data we have. No reference line in this unit: a rolling median of the user's own history drifts 2.1x across four weeks with no behaviour change, so it would read as absolute while moving; instead `config.intensity_axis_max_tokens` is a *stated* ceiling (default 1M, clipping 4.5% of active buckets; 500k was tried and reverted at 15.6% overall / 25.8% of a busy week)), `token_scan.rs` (60s tree scan of `~/.claude/projects/**/*.jsonl` with a per-file byte cursor in `token_scan_cursor.json`, feeding the store. Deliberately *not* an extension of `log_watcher`, which tails one hook-supplied `transcript_path` per chat_id and so never opens `<session>/subagents/**.jsonl` — 616 of 660 files carrying 55.5% of all output tokens — and whose extraction is first-wins, sidechain-blind and has no `output_tokens` field because it feeds the context gauge. Resolves the root from `CLAUDE_CONFIG_DIR` else `$HOME/.claude`; the env var is real (it is in the 2.1.238 binary) but a GUI app on macOS inherits no shell profile, so the fallback is the live path — hence the resolved root and file count are logged every pass and a zero-file pass warns rather than passing silently. Logged `token_scan`), `remote_tokens.rs` (`RemoteTokenStore` — per-device token records under `remote_tokens/`, mirroring `remote_usage.rs` and differing in exactly one place: **acceptance gates on `seq`, never `ts`**. `remote_usage` can gate on `ts > held_max` only because a single sequential poller emits strictly increasing timestamps; token records violate that in ordinary operation — concurrent session tails append in scan order, a fan-out revision re-appends an older `ts`, and the historical import writes weeks below the current max — and under a `ts` gate each is dropped with no branch, no counter and no log, invisibly, since a missing bucket looks exactly like an idle one. `sync.rs` advertises `token_tip` (`serde(default)`, so a peer on an older build parses and contributes nothing) and serves `GET /api/sync/tokens?since=`; `commands::merged_token_records` unions local + every peer *before* reducing, since one `message.id` can arrive from two devices), `auto_resize.rs` (Up/Down content-fit window with edge anchor; a cross-platform vertical resize lock (`resize_lock`) that keeps a manual edge drag from fighting the content fit while leaving width to the user — its blind spot, maximizing, is closed one level up by `"maximizable": false` on the main window in `tauri.conf.json`, which drops `WS_MAXIMIZEBOX` so a header drag to the top edge can't snap-maximize and makes Tauri's drag-region double-click (`internal_toggle_maximize`, gated on `is_maximizable()`) inert in the maximize direction only, so an already-maximized window can still be restored; see the `install_resize_lock` doc for why it isn't tied to a fit mode — on Windows a `WM_NCHITTEST`/`WM_NCLBUTTONDOWN` subclass neutralizing the top/bottom/corner hit-tests, on macOS a min == max content-height pin (`set_size_constraints`) rebuilt from the window's `tauri.conf.json` bounds on every apply so the declared `minWidth` survives the four-bounds write, since an undecorated NSWindow keeps `NSWindowStyleMask::Resizable` and stays edge-resizable. `engage` runs *before* the resize, not after: a pin left from the previous apply would otherwise clamp `set_size` back to the old height, and engaging first is the only ordering that holds whether the platform applies the resize inline (Windows) or defers it to the main queue (macOS). A minimize guard (`is_minimized`) fronts `apply`: a minimized window reports the OS's iconic rect rather than its own geometry (on Windows `outer_position` reads (-32000, -32000) and `inner_size` reads SM_CXMINIMIZED x SM_CYMINIMIZED, 237x39 at 144 DPI), so the anchor arithmetic, the work-area clamp (which always resolves to a corner, the iconic rect overlapping no monitor) and the carried-over width are all computed from a rect that isn't the window's — which is how a full-screen game, which minimizes the always-on-top widget, left it collapsed to a header sliver. The same guard fronts `commands::ensure_window_on_screen` (a minimized window is off every monitor by construction, so the off-screen rescue would otherwise fire on every show-while-minimized) and `commands::set_compact_width` (reachable on the usage-poll cadence for as long as the widget stays minimized). It is keyed on minimized and deliberately NOT on visibility: a window hidden to the tray keeps a real rect, and skipping there would bring the widget back stale on every tray toggle. Recovery cannot start in the frontend — minimizing never resizes the WebView2 child, so `window.innerHeight` stays frozen at its pre-minimize value across the whole round trip and every viewport-keyed self-heal (the `vh * 2 < desired` collapse heal included) reads the window as already fitting — so `lib.rs`'s `refit_after_restore` folds `WindowEvent::Resized` (emitted for both edges, and for our own resizes) down to the minimized->restored edge via `resized_is_restore` and emits `refit_window`, which `App.svelte` answers with a dedup-disarmed `forceMeasure`. Inert on macOS, where a miniaturized `NSWindow` keeps its real frame and tao emits no `Resized` on either edge — nothing to corrupt, so nothing to recover. Managing frontend-read state there is a structural fix for the whole class of mount-time `State` races — `get_config` latching `Config::default()` (auto_resize `None` → frozen window), `frontend_log` dropping every early log, `get_setup_state` flashing the onboarding panel — so `.setup()` (which runs later at Ready, after the webviews exist) does only window/tray/service wiring and reads config from the already-managed state, never managing frontend-read state itself. Must run before window creation because config-defined webviews start loading immediately.
